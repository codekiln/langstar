# Design: Graph/Deployment CLI Separation

**Issue:** #562 (527.2-design)
**Parent:** #527 (ls-graph-deployments-separation milestone)
**Date:** 2025-12-05

## Executive Summary

This document consolidates research findings from #528 and establishes design decisions for separating `langstar graph` and `langstar deployment` commands. The key insight is that **graphs are NOT first-class API resources** - they're derived from assistants and accessed via the Agent Server API, while deployments are managed through the Control Plane API.

---

## 1. Research Summary (from #528)

### 1.1 Key Finding: Graphs are Derived Entities

- **No `/graphs` list endpoint exists** in Control Plane, LangSmith, or Agent Server APIs
- **Graphs are defined in `langgraph.json`** at deployment time
- **Each assistant has a `graph_id` field** linking it to its underlying graph
- **Graph structure is accessible** via `/assistants/{id}/graph?xray=true`

### 1.2 Available Graph-Related Endpoints (Agent Server API)

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/assistants/{id}/graph` | GET | Get graph structure (accepts assistant_id OR graph_id) |
| `/assistants/{id}/graph?xray=true` | GET | Include subgraph representation |
| `/assistants/{id}/subgraphs` | GET | List subgraphs |
| `/assistants/{id}/schemas` | GET | Get graph schemas |
| `/assistants/search` | POST | Search assistants (used to derive graph list) |

### 1.3 Graph Structure Response

```json
{
    "nodes": [
        { "id": "__start__", "type": "runnable", "data": { "name": "__start__" } },
        { "id": "Responder", "type": "runnable", "data": { "name": "Responder" } },
        { "id": "Feedback", "type": "runnable", "data": { "name": "Feedback" } },
        { "id": "__end__" }
    ],
    "edges": [
        { "source": "Responder", "target": "Feedback", "conditional": true },
        { "source": "Responder", "target": "__end__", "conditional": true },
        { "source": "__start__", "target": "Feedback", "conditional": true },
        { "source": "__start__", "target": "Responder", "conditional": true },
        { "source": "Feedback", "target": "__end__" }
    ]
}
```

## 2. DX Consistency Analysis

### 2.1 Existing Command Patterns

| Command | Subcommands | Deployment Arg | Pattern Notes |
|---------|-------------|----------------|---------------|
| `assistant` | list, search, get, create, update, delete | `--deployment <name-or-id>` (required) | Uses Agent Server API |
| `graph` (current) | list, get, create, delete | N/A (is the deployment) | Uses Control Plane API |
| `runs` | query | `--project <name-or-uuid>` | Uses LangSmith API |
| `queue` | list, get, create, delete, add-runs, runs | N/A | Uses LangSmith API |
| `prompt` | list, get, create, update, delete | N/A | Uses LangSmith API |

### 2.2 Flag Naming Conventions

**From existing commands:**
- `-f, --format` - Output format (global)
- `-l, --limit` - Maximum results
- `-o, --offset` - Pagination offset
- `--deployment` - Deployment name or ID (required for Agent Server API commands)
- `-y, --yes` or `--force` - Skip confirmation prompts

**New commands should follow:**
- `langstar deployment list` - No deployment flag (lists deployments themselves)
- `langstar graph list <deployment>` - Positional arg for deployment (consistent with being required)
- `langstar graph get <graph_id> --deployment <deployment>` - Required flag pattern

### 2.3 Output Format Consistency

**Standard formats:**
- `json` - Machine-readable, default when piped
- `table` - Human-readable, default for TTY

**Table columns for graphs (proposed):**

```
╭──────────────┬─────────────────────┬────────────┬─────────────────────╮
│ Graph ID     │ Assistants          │ # Assists  │ Nodes               │
├──────────────┼─────────────────────┼────────────┼─────────────────────┤
│ agent        │ default, custom-v1  │ 2          │ Responder, Feedback │
│ rag_pipeline │ rag-assistant       │ 1          │ Retriever, Generate │
╰──────────────┴─────────────────────┴────────────┴─────────────────────╯
```

### 2.4 Error Message Patterns

**Existing patterns from `assistant.rs`:**
```
Deployment '{name}' not found. Run 'langstar graph list' to see available deployments.
```

**After migration:**
```
Deployment '{name}' not found. Run 'langstar deployment list' to see available deployments.
```

## 3. Configuration Integration

### 3.1 Environment Variables

**Existing (no changes needed):**

| Variable | Purpose | Used By |
|----------|---------|---------|
| `LANGSMITH_API_KEY` | API authentication | All commands |
| `LANGGRAPH_API_KEY` | LangGraph-specific auth (optional) | Deployment commands |
| `LANGSMITH_WORKSPACE_ID` | Workspace scoping | All commands |
| `LANGSMITH_ORGANIZATION_ID` | Org scoping | All commands |
| `LANGGRAPH_GITHUB_INTEGRATION_ID` | GitHub integration for deployments | `deployment create` |
| `LANGSTAR_OUTPUT_FORMAT` | Default output format | All commands |

**No new environment variables required** for graph/deployment separation.

### 3.2 Precedence Order

Following established pattern from `cli/src/config.rs`:

1. **CLI flags** (highest priority)
2. **Environment variables**
3. **Config file** (`~/.config/langstar/config.toml`)
4. **Default values** (lowest priority)

### 3.3 Deployment Name-vs-ID Resolution

**Existing pattern from `assistant.rs:166-198`:**

```rust
async fn resolve_deployment_url(config: &Config, deployment_name_or_id: &str) -> Result<String> {
    let client = LangchainClient::new(auth)?;
    let deployments_list = client.deployments().list(Some(100), Some(0), None).await?;

    let deployment = deployments_list.resources.iter()
        .find(|d| d.name == deployment_name_or_id || d.id == deployment_name_or_id)
        .ok_or_else(|| CliError::Config(format!(
            "Deployment '{}' not found...", deployment_name_or_id
        )))?;

    deployment.custom_url().ok_or_else(|| CliError::Config(...))
}
```

**Design decision:** Extract this function to a shared module for reuse by both `assistant` and `graph` commands.

## 4. Command Specifications

### 4.1 `langstar deployment` (Renamed from `graph`)

**Semantics:** Manage LangGraph Cloud deployments via Control Plane API

```bash
# List all deployments
langstar deployment list [--limit N] [--offset N] [--deployment-type TYPE] [--status STATUS]

# Get deployment details
langstar deployment get <deployment_id>

# Create new deployment
langstar deployment create --name NAME --source github --repo-url URL --branch BRANCH [--wait]

# Delete deployment
langstar deployment delete <deployment_id> [--yes]
```

**Implementation:** Rename `cli/src/commands/graph.rs` → `deployment.rs`, update enum names.

### 4.2 `langstar graph` (New Implementation)

**Semantics:** Inspect LangGraph graphs within deployments via Agent Server API

```bash
# List graphs in a deployment
langstar graph list <deployment> [--show-nodes]

# Get graph structure
langstar graph get <graph_id> --deployment <deployment> [--xray]
```

**Implementation details:**

**`graph list` algorithm:**
1. Resolve deployment name/ID to URL (reuse `resolve_deployment_url`)
2. Call `POST /assistants/search` to get all assistants
3. Extract unique `graph_id` values
4. Optionally fetch node info for each graph via `/assistants/{graph_id}/graph`
5. Display aggregated results

**`graph get` algorithm:**
1. Resolve deployment name/ID to URL
2. Call `GET /assistants/{graph_id}/graph?xray={xray}`
3. Display graph structure (nodes, edges)

### 4.3 Argument Design Rationale

**Why positional `<deployment>` for `graph list`?**
- Deployment is always required (graphs exist within deployments)
- Follows pattern: `langstar <resource> <action> <required-context>`
- More ergonomic: `langstar graph list my-deployment` vs `langstar graph list --deployment my-deployment`

**Why `--deployment` flag for `graph get`?**
- Graph ID is the primary identifier (positional)
- Deployment provides context (flag)
- Follows existing `assistant get <id> --deployment <d>` pattern

## 5. Backward Compatibility

### 5.1 Deprecation Strategy

**Option A (Recommended): Semantic Break with Deprecation Wrapper**

Old `langstar graph list` now has new semantics (lists graphs, not deployments), but we provide a deprecation path:

```
⚠️  Command semantics changed in v0.x.0

  'langstar graph list' now lists graphs within a deployment.

  To list deployments (previous behavior), use:
    langstar deployment list

  To list graphs in a deployment, use:
    langstar graph list <deployment-name-or-id>
```

**Option B: Hidden Alias (Not Recommended)**

Keep old behavior with `#[command(hide = true)]` - confuses users who expect new semantics.

## 6. API Mapping Summary

| CLI Command | API | Endpoint |
|-------------|-----|----------|
| `deployment list` | Control Plane | `GET /v2/deployments` |
| `deployment get` | Control Plane | `GET /v2/deployments/{id}` |
| `deployment create` | Control Plane | `POST /v2/deployments` |
| `deployment delete` | Control Plane | `DELETE /v2/deployments/{id}` |
| `graph list` | Agent Server | `POST /assistants/search` → derive unique graph_ids |
| `graph get` | Agent Server | `GET /assistants/{graph_id}/graph?xray=true` |
