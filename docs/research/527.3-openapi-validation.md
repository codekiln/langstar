## 3. Schema Validation

### 3.1 Graph Topology Response

**Research expectation** (from #528):
```json
{
  "nodes": [
    { "id": "__start__", "type": "runnable", "data": { "name": "__start__" } }
  ],
  "edges": [
    { "source": "Responder", "target": "Feedback", "conditional": true }
  ]
}
```

**OpenAPI schema** (loosely typed):
```json
{
  "additionalProperties": { "items": { "type": "object" }, "type": "array" },
  "type": "object"
}
```

**Live API response** (verified):
```json
{
  "nodes": [
    { "id": "__start__", "type": "runnable", "data": { "name": "__start__" } },
    { "id": "echo", "type": "runnable", "data": { "name": "echo" } },
    { "id": "__end__" }
  ],
  "edges": [
    { "source": "__start__", "target": "echo" },
    { "source": "echo", "target": "__end__" }
  ]
}
```

**Finding**: The OpenAPI schema is intentionally loose (allows arbitrary object with arrays). The actual response structure matches #528's documentation. The `conditional` field appears only on edges with conditional routing (not present in simple linear graphs).

### 3.2 Assistant Schema (graph_id Field)

**Research expectation**: Assistants have a `graph_id` field linking them to their graph.

**OpenAPI definition** (`components.schemas.Assistant.properties.graph_id`):
```json
{
  "type": "string",
  "title": "Graph Id",
  "description": "The ID of the graph."
}
```

**Validation Status: PASS** - `graph_id` field confirmed in Assistant schema.

### 3.3 GraphSchema (for /schemas endpoint)

**OpenAPI definition** (`components.schemas.GraphSchema`):
```json
{
  "properties": {
    "graph_id": { "type": "string" },
    "input_schema": { "type": "object" },
```

## 5. Implementation Recommendations

Based on this validation:

### 5.1 Confirmed Design Decisions

1. **Graph listing via assistants** - No `/graphs` endpoint exists. List graphs by:
   - Call `POST /assistants/search`
   - Extract unique `graph_id` values
   - Optionally fetch topology for each

2. **Graph topology via graph_id** - The `/assistants/{id}/graph` endpoint accepts `graph_id` directly, simplifying the implementation.

3. **xray parameter** - Use `?xray=true` to include subgraph details in topology response.

### 5.2 SDK Type Definitions

Recommended Rust types (confirming #528 proposal):

```rust
#[derive(Debug, Deserialize, Serialize)]
pub struct GraphTopology {
    pub nodes: Vec<GraphNode>,
    pub edges: Vec<GraphEdge>,
}

#[derive(Debug, Deserialize, Serialize)]
pub struct GraphNode {
    pub id: String,
    #[serde(rename = "type")]
    pub node_type: Option<String>,
    pub data: Option<GraphNodeData>,
}

#[derive(Debug, Deserialize, Serialize)]
pub struct GraphNodeData {
    pub name: String,
}

#[derive(Debug, Deserialize, Serialize)]
pub struct GraphEdge {
    pub source: String,
    pub target: String,
    #[serde(default)]
    pub conditional: bool,
}
```

### 5.3 OpenAPI Spec Quality Note

The graph topology response uses a loose schema that doesn't document the nodes/edges structure. This is acceptable but means:
- SDK types are based on empirical testing, not schema
- Future API changes may not be reflected in OpenAPI first
- Consider filing upstream issue to improve schema precision
