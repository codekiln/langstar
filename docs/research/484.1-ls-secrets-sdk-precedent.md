# Workspace Secrets SDK Precedent Research

**Issue**: #487 (Phase 1 of #484)
**Parent**: #484 (ls-secrets milestone)
**Date**: 2025-12-01
**Status**: Complete

## Executive Summary

This document analyzes existing Langstar SDK patterns to ensure consistency when implementing the workspace secrets SDK. The analysis confirms that workspace secrets follow the same patterns as other workspace resources (datasets, playground settings), with special considerations for security-sensitive operations.

**Key Finding**: Secrets API uses a **POST-based upsert pattern** (not traditional CRUD), which differs slightly from other resources but aligns with security best practices.

## 1. SDK Architecture Patterns

### 1.1 Type Definition Conventions

Based on analysis of `sdk/src/datasets.rs`, `sdk/src/deployments.rs`, and `sdk/src/organization.rs`:

**Pattern**: Separate types for requests, responses, and operations

```rust
// Response type - represents API response
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Resource {
    pub id: Uuid,
    pub name: String,
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
    // ... other fields
}

// Create request - all required fields
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ResourceCreate {
    pub name: String,
    // Optional fields use Option<T>
    pub description: Option<String>,
    // ... other fields
}

// Update request - all fields optional for partial updates
#[derive(Debug, Clone, Serialize, Deserialize, Default)]
pub struct ResourceUpdate {
    #[serde(skip_serializing_if = "Option::is_none")]
    pub name: Option<String>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub description: Option<String>,
    // ... other fields
}

// List parameters - filtering and pagination
#[derive(Debug, Clone, Default)]
pub struct ListResourceParams {
    pub limit: Option<u32>,
    pub offset: Option<u32>,
    pub name_contains: Option<String>,
    // ... filter fields
}
```

**Key conventions**:
- `#[derive(Debug, Clone, Serialize, Deserialize)]` on all types
- `#[serde(skip_serializing_if = "Option::is_none")]` for optional fields in update requests
- `Default` implementation for parameter structs
- `DateTime<Utc>` from chrono for timestamps
- `Uuid` for IDs where applicable

**Characteristics**:

#### List Pattern

```rust
/// List all resources with optional filtering
pub async fn list_resources(
    &self,
    params: crate::module::ListResourceParams,
) -> Result<Vec<crate::module::Resource>> {
    let mut request = self.langsmith_get("/api/v1/resources")?;

    // Add query parameters conditionally
    if let Some(limit) = params.limit {
        request = request.query(&[("limit", limit)]);
    }
    if let Some(offset) = params.offset {
        request = request.query(&[("offset", offset)]);
    }
    if let Some(filter) = &params.filter_field {
        request = request.query(&[("filter_field", filter)]);
    }

    self.execute(request).await
}
```

**Characteristics**:
- Takes structured params type with all optional fields
- Returns `Vec<T>` of items directly (no wrapper)
- Conditionally adds query parameters for non-None values
- Does NOT auto-paginate (returns single page)

#### Get Pattern

```rust
/// Get a single resource by ID
pub async fn get_resource(&self, resource_id: uuid::Uuid) -> Result<crate::module::Resource> {
    let path = format!("/api/v1/resources/{}", resource_id);

    self.execute(request).await
}
```

**Characteristics**:
- Takes ID as parameter (UUID or String depending on API)
- Returns single item
- Simple path interpolation

```rust

pub async fn update_resource(

**Characteristics**:

## 2. Secrets API Specific Patterns

### 2.1 Upsert Pattern vs Traditional CRUD

**Finding**: Secrets API uses POST for both create AND update (upsert), which differs from traditional CRUD.

**Traditional CRUD** (e.g., datasets):
```
POST   /api/v1/datasets          → Create
GET    /api/v1/datasets          → List
GET    /api/v1/datasets/{id}     → Get
PATCH  /api/v1/datasets/{id}     → Update
DELETE /api/v1/datasets/{id}     → Delete
```

**Secrets API** (upsert pattern):
```
POST /api/v1/workspaces/current/secrets → Upsert (create OR update)
GET  /api/v1/workspaces/current/secrets → List keys only
```

**Rationale** (based on scout #456):
1. **Security**: No GET by ID prevents accidental value exposure
2. **Simplicity**: Single operation for create/update reduces API surface
3. **Idempotency**: Multiple POSTs with same key are safe
4. **Batch support**: POST accepts array of secrets

### 2.2 Security Considerations

**Critical**: Secret values are NEVER returned in API responses.

**API responses**:
```rust
// List endpoint returns ONLY keys, never values
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct SecretKey {
    pub key: String,
}

// Upsert endpoint accepts values but returns empty/null
```

**Implication for SDK design**:
- No `get_secret_by_key()` method (API doesn't support it)
- `list_secrets()` returns `Vec<SecretKey>` (keys only)
- `upsert_secrets()` returns `()` or confirmation (no values)

**References**:
- `docs/research/456-ls-secrets-scout.md:72-101` - SecretKey response schema
- `docs/research/456-ls-secrets-scout.md:102-150` - SecretUpsert request schema

### 2.3 Permission Requirements

**Finding** (from scout #456 experiments):

Standard API keys can LIST secrets but need `workspaces:manage` permission for write operations.

| Operation | Permission | Error if missing |
|-----------|-----------|-----------------|
| List secrets | Standard | ✅ Works |
| Create secret | workspaces:manage | 403 Forbidden |
| Update secret | workspaces:manage | 403 Forbidden |
| Delete secret | workspaces:manage | 403 Forbidden |

**Error response** (403):
```json
{
  "detail": "Permission denied, you do not have the required permission workspaces:manage"
}
```

**Implication**: SDK should handle 403 gracefully, possibly with helpful error messages.

**References**:
- `docs/research/456-ls-secrets-scout.md:192-212` - Permission requirements

### 2.4 Deletion Pattern

**Finding**: No DELETE endpoint. Deletion via `POST` with `value: null`.

```rust
// Delete by upserting with null value
SecretUpsert {
    key: "SECRET_KEY".to_string(),
    value: None,  // null in JSON
}
```

**Implication**: SDK should provide explicit `delete_secret()` method that internally uses upsert with null value.

**References**:
- `docs/research/456-ls-secrets-scout.md:146-150` - value can be null (deletion)

## 3. Recommended SDK Types for Secrets

Based on established patterns and secrets API specifics:

```rust
// sdk/src/secrets.rs

use serde::{Deserialize, Serialize};

/// A workspace secret key (response from list endpoint).
///
/// Security: Values are NEVER returned by the API.
///
/// # API Reference
///
/// - Maps to `SecretKey` in OpenAPI spec
/// - Returned by: `GET /api/v1/workspaces/current/secrets`
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct SecretKey {
    /// The secret key name (e.g., "ANTHROPIC_API_KEY")
    pub key: String,
}

/// Request to create or update workspace secrets.
///
/// # API Reference
///
/// - Maps to `SecretUpsert` in OpenAPI spec
/// - Used by: `POST /api/v1/workspaces/current/secrets`
///
/// # Notes
///
/// - Set `value` to `None` to delete a secret
/// - This type is used for both create AND update operations (upsert pattern)
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct SecretUpsert {
    /// The secret key name
    pub key: String,

    /// The secret value, or None to delete
    ///
    /// Setting this to `None` deletes the secret from the workspace.
    #[serde(skip_serializing_if = "Option::is_none")]
    pub value: Option<String>,
}

impl SecretUpsert {
    /// Create a new secret upsert request to set a value
    pub fn set(key: impl Into<String>, value: impl Into<String>) -> Self {
        Self {
            key: key.into(),
            value: Some(value.into()),
        }
    }

    /// Create a new secret upsert request to delete a secret
    pub fn delete(key: impl Into<String>) -> Self {
        Self {
            key: key.into(),
            value: None,
        }
    }
}
```

**Design decisions**:
1. **No `Secret` type**: API never returns values, so no need for a type with both key and value
2. **SecretUpsert for both create/update**: Matches upsert API pattern
3. **Option<String> for value**: Supports both set and delete operations
4. **Convenience methods**: `set()` and `delete()` improve ergonomics
5. **No ID field**: Secrets are identified by key name, not UUID

## 4. Recommended Client Methods

Based on established patterns and secrets API:

```rust
// sdk/src/client.rs

impl LangchainClient {
    /// List all workspace secret keys.
    ///
    /// Security: This endpoint returns ONLY secret keys, never values.
    /// This is by design to prevent accidental exposure of sensitive data.
    ///
    /// # Example
    ///
    /// ```no_run
    /// # use langstar_sdk::{AuthConfig, LangchainClient};
    /// # async fn example() -> langstar_sdk::Result<()> {
    /// let auth = AuthConfig::from_env()?;
    /// let client = LangchainClient::new(auth)?;
    ///
    /// let keys = client.list_workspace_secrets().await?;
    /// for key in keys {
    ///     println!("Secret: {}", key.key);
    /// }
    /// # Ok(())
    /// # }
    /// ```
    ///
    /// # API Reference
    ///
    /// - Endpoint: `GET /api/v1/workspaces/current/secrets`
    /// - Requires: Standard API key
    /// - OpenAPI spec: <https://api.smith.langchain.com/openapi.json>
    pub async fn list_workspace_secrets(&self) -> Result<Vec<crate::secrets::SecretKey>> {
        let request = self.langsmith_get("/api/v1/workspaces/current/secrets")?;
        self.execute(request).await
    }

    /// Create or update workspace secrets (upsert operation).
    ///
    /// This method accepts an array of secrets to create or update in a single request.
    /// If a secret with the given key already exists, it will be updated.
    /// To delete a secret, set its value to `None`.
    ///
    /// # Arguments
    ///
    /// * `secrets` - Array of secret upsert requests
    ///
    /// # Permissions
    ///
    /// Requires API key with `workspaces:manage` permission.
    /// Will return 403 Forbidden if permission is missing.
    ///
    /// # Example
    ///
    /// ```no_run
    /// # use langstar_sdk::{AuthConfig, LangchainClient};
    /// # use langstar_sdk::secrets::SecretUpsert;
    /// # async fn example() -> langstar_sdk::Result<()> {
    /// let auth = AuthConfig::from_env()?;
    /// let client = LangchainClient::new(auth)?;
    ///
    /// // Create/update secrets
    /// let secrets = vec![
    ///     SecretUpsert::set("ANTHROPIC_API_KEY", "sk-ant-..."),
    ///     SecretUpsert::set("OPENAI_API_KEY", "sk-..."),
    /// ];
    /// client.upsert_workspace_secrets(secrets).await?;
    ///
    /// // Delete a secret
    /// let delete = vec![SecretUpsert::delete("OLD_KEY")];
    /// client.upsert_workspace_secrets(delete).await?;
    /// # Ok(())
    /// # }
    /// ```
    ///
    /// # API Reference
    ///
    /// - Endpoint: `POST /api/v1/workspaces/current/secrets`
    /// - Requires: API key with `workspaces:manage` permission
    /// - OpenAPI spec: <https://api.smith.langchain.com/openapi.json>
    pub async fn upsert_workspace_secrets(
        &self,
        secrets: Vec<crate::secrets::SecretUpsert>,
    ) -> Result<()> {
        let request_builder = self
            .langsmith_post("/api/v1/workspaces/current/secrets")?
            .json(&secrets);
        // API returns empty object {} or null (per scout #456)
        self.execute_status_only_request(request_builder).await
    }

    /// Delete a workspace secret.
    ///
    /// This is a convenience method that internally calls `upsert_workspace_secrets`
    /// with a null value for the specified key.
    ///
    /// # Arguments
    ///
    /// * `key` - The secret key to delete
    ///
    /// # Permissions
    ///
    /// Requires API key with `workspaces:manage` permission.
    ///
    /// # Example
    ///
    /// ```no_run
    /// # use langstar_sdk::{AuthConfig, LangchainClient};
    /// # async fn example() -> langstar_sdk::Result<()> {
    /// let auth = AuthConfig::from_env()?;
    /// let client = LangchainClient::new(auth)?;
    ///
    /// client.delete_workspace_secret("OLD_API_KEY").await?;
    /// # Ok(())
    /// # }
    /// ```
    ///
    /// # API Reference
    ///
    /// - Endpoint: `POST /api/v1/workspaces/current/secrets` (with value: null)
    /// - Requires: API key with `workspaces:manage` permission
    pub async fn delete_workspace_secret(&self, key: impl Into<String>) -> Result<()> {
        let secrets = vec![crate::secrets::SecretUpsert::delete(key)];
        self.upsert_workspace_secrets(secrets).await
    }
}
```

**Design decisions**:
1. **Method naming**:
   - `list_workspace_secrets()` - explicit about workspace scoping
   - `upsert_workspace_secrets()` - reflects true API behavior (not "create" or "update")
   - `delete_workspace_secret()` - convenience wrapper, singular (deletes one)

2. **Batch support**:
   - `upsert_workspace_secrets()` accepts `Vec` for batch operations
   - Matches API design (accepts arrays)

3. **Convenience methods**:
   - `delete_workspace_secret()` singular method for ergonomics
   - Internally uses `upsert` with null value

4. **Return types**:
   - `list` returns `Vec<SecretKey>` (keys only, no values)
   - `upsert` returns `()` (no response body from API)
   - `delete` returns `()` (delegating to upsert)

5. **Documentation**:
   - Explicit security notes about values never being returned
   - Permission requirements clearly stated
   - Example code for common use cases

## 5. Comparison with Other Resources

| Aspect | Datasets (Standard CRUD) | Secrets (Upsert Pattern) |
|--------|-------------------------|-------------------------|
| **Create** | `POST /api/v1/datasets` → Dataset | `POST /api/v1/workspaces/current/secrets` → void |
| **List** | `GET /api/v1/datasets` → Dataset[] | `GET /api/v1/workspaces/current/secrets` → SecretKey[] |
| **Get by ID** | `GET /api/v1/datasets/{id}` → Dataset | ❌ Not supported (security) |
| **Update** | `PATCH /api/v1/datasets/{id}` → Dataset | `POST /api/v1/workspaces/current/secrets` (upsert) |
| **Delete** | `DELETE /api/v1/datasets/{id}` → void | `POST /api/v1/workspaces/current/secrets` (value: null) |
| **Batch ops** | One at a time | Array support built-in |
| **Response** | Full object with data | Keys only (no values) |
| **Permissions** | Standard API key | Needs `workspaces:manage` for writes |

**Key differences**:
1. **No GET by ID**: Secrets can't be retrieved individually by key for security
2. **No separate update**: POST serves as both create and update (upsert)
3. **No DELETE endpoint**: Deletion via POST with null value
4. **Keys-only responses**: List never returns values
5. **Elevated permissions**: Write operations require `workspaces:manage`
6. **Batch first**: API designed for array inputs

## 7. Testing Strategy

### 7.1 Unit Tests

Following patterns from `sdk/src/organization.rs:93-144`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_secret_key_deserialization() {
        let json = r#"{"key": "ANTHROPIC_API_KEY"}"#;
        let key: SecretKey = serde_json::from_str(json).unwrap();
        assert_eq!(key.key, "ANTHROPIC_API_KEY");
    }

    #[test]
    fn test_secret_upsert_set() {
        let upsert = SecretUpsert::set("KEY", "value");
        assert_eq!(upsert.key, "KEY");
        assert_eq!(upsert.value, Some("value".to_string()));
    }

    #[test]
    fn test_secret_upsert_delete() {
        let upsert = SecretUpsert::delete("KEY");
        assert_eq!(upsert.key, "KEY");
        assert_eq!(upsert.value, None);
    }

    #[test]
    fn test_secret_upsert_serialization() {
        // With value
        let upsert = SecretUpsert::set("KEY", "value");
        let json = serde_json::to_string(&upsert).unwrap();
        assert!(json.contains(r#""key":"KEY""#));
        assert!(json.contains(r#""value":"value""#));

        // Without value (delete)
        let upsert = SecretUpsert::delete("KEY");
        let json = serde_json::to_string(&upsert).unwrap();
        assert!(json.contains(r#""key":"KEY""#));
        assert!(!json.contains("value"));
    }
}

async fn test_secrets_lifecycle() {

## 8. Key Takeaways for Implementation

1. **Follow upsert pattern**: Don't try to force traditional CRUD onto secrets API
2. **Security-first**: Never log, print, or expose secret values in SDK
3. **Use existing patterns**: Type definitions, error handling, and scoping all follow established conventions
4. **Convenience methods**: Provide ergonomic wrappers (e.g., `delete_workspace_secret()`) even though API uses upsert
5. **Batch support**: Accept arrays in SDK methods to match API design
6. **Permission awareness**: Document `workspaces:manage` requirement clearly
7. **No GET by key**: Don't try to implement retrieval of individual secrets
8. **Integration tests**: Require elevated API key for CI/testing
